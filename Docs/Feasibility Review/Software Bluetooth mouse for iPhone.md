# Spare Android phones can replace the ESP32

_Written 2026-10-29 for the Mantiza team. Based on four research notes dated 2026-10-28._

**Short answer: partly.** Mantiza **cannot** be its own mouse on the same iPhone, and no other software-only trick on a single stock iPhone can tap inside other apps. But many users already own a second device that can play the "hands" role. The best-supported choice is a **spare Android phone (Android 9 or newer)**. Android has a public API, `BluetoothHidDevice`, that lets an ordinary app act as a Bluetooth Classic mouse and keyboard. Free apps built on it say they work with iOS and iPadOS. A **Mac** is the second option: the KeyPad app on the Mac App Store advertises "basic mouse functions for iPhones via Assistive Touch". That is the only listing we found that names the iPhone AssistiveTouch pointer, but the Mac has to stay on and nearby. A **spare iPhone or iPad** is a real but unproven third option. The notes disagree here, and both are half right: iOS blocks the short HID service ID, but developers report that the long form of the same ID gets through, and one App Store app claims an iPhone can drive an iPad as a mouse. Nobody has shown it driving another iPhone. Our recommendation is to keep the ESP32 as the reliable default and to build Mantiza around one command protocol with swappable "hands", so the same app can drive an ESP32, an Android helper app, or later a Mac or spare-iPhone helper. Two weeks of cheap tests with off-the-shelf apps answer the open questions before we write much code.

**Confidence markers used in this report.** **[confirmed]** means official docs (Apple, Google, Microsoft) or an Apple engineer's reply. **[reported]** means one or a few non-official sources: a vendor listing, a project README, or a forum post. **[unconfirmed]** means our own inference, or a claim no source backs; treat these as things to test.

## No software route works on a single iPhone

The obvious idea is to have the Mantiza app pretend to be a Bluetooth mouse for its own iPhone. That fails at two levels. First, iOS blocks apps from publishing the standard HID service. Adding service `1812` with `CBPeripheralManager` returns `CBErrorDomain Code=8 "The specified UUID is not allowed for this operation"`. This has been **[reported]** by several developers from 2013 to 2024 ([Apple Dev Forums 725238](https://developer.apple.com/forums/thread/725238)). In May 2026 an Apple engineer **[confirmed]** that "advertising certain services/characteristics is restricted by the system" ([Apple Dev Forums 826714](https://developer.apple.com/forums/thread/826714)). Second, even if an app got past that block, the phone would have to discover and pair with its own radio. Bluetooth links are built between two devices with different addresses, and no source shows an iPhone listing itself under AssistiveTouch > Devices > Bluetooth Devices. So same-phone "loopback" is **[unconfirmed] but almost certainly impossible**. One afternoon of testing would settle it (test S1 below).

The other software-only routes all fail for a normal user. No public iOS API lets one app inject taps into another. The private touch APIs (`IOHIDEvent`) have been locked to system processes since about iOS 6–7 ([Stack Overflow archive](https://kaweah.freedombox.rocks/kiwix/stackoverflow.com_en_all_2023-11/questions/26916379/ios7-8-send-touch-events-on-non-jailbroken-iphone-pad)). Using them breaks App Review guideline 2.5.1, which also applies to EU Notarization **[confirmed]** ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). WebDriverAgent/XCUITest really can tap any app. But on iOS 17+ it "immediately stops" when the phone disconnects from the Mac that started it **[reported]** ([Appium Discuss](https://discuss.appium.io/t/running-wda-on-ios-17/42392)). It also needs Developer Mode and re-signing every 7 days on a free account or once a year on a paid one ([Jean Galea](https://jeangalea.com/control-automate-iphone-webdriveragent/)). Tools like StikDebug show an iPhone can open developer-service connections to itself through a loopback VPN, but they only use this for JIT. Starting a full test session that way is **[unconfirmed]**, and the loopback broke for a while on an iOS 26.4 beta ([StikDebug](https://github.com/StephenDev0/StikDebug)). Switch Control's "Use Other Devices" needs a second Apple device and a switch, and a person still operates the scanning **[confirmed]** ([Apple Support 118667](https://support.apple.com/118667)). Voice Control can tap by label or grid **[confirmed]** ([Apple Support HT210418](https://support.apple.com/HT210418)). Having Mantiza "speak" commands to it through the phone's own speaker has never been tested, and it would be slow and noisy. App Intents and Siri in iOS 27 only expose each app's own declared actions, not general control of other apps' screens **[reported]** ([Braze](https://www.braze.com/resources/articles/2026-wwdc-ios-27-updates)). The conclusion is that a second device is always needed. The real question is whether it can be one the user already owns.

## An Android phone is the best-supported free "hands"

Android 9 added `BluetoothHidDevice`. This public API lets an app register its own HID report descriptor and act as a **Bluetooth Classic mouse, keyboard, or both** **[confirmed: the class and its companion classes are in the Android reference]** ([Android reference](https://developer.android.com/reference/android/bluetooth/BluetoothHidDevice)). Google's own Wear OS sample uses it as an air mouse ([ginkage/wearmouse](https://github.com/ginkage/wearmouse)). Several apps already ship on it and name Apple devices as hosts. Appground's "Bluetooth Keyboard & Mouse", on Google Play, lists **Apple iOS and iPadOS as "successfully tested"** **[reported]** ([BlueStacks listing](https://www.bluestacks.com/campaign/io.appground.blek/en)). The open-source Bluetooth Remote (GPL-3.0, Android 9+, updated June 2026) claims **"full support on iOS/iPadOS 13+"** **[reported]** ([F-Droid](https://f-droid.org/packages/io.github.jqssun.btremote/)). Classic HID is also how ordinary Bluetooth mice pair with AssistiveTouch, so Android avoids the BLE pairing and bonding problems that Linux boards hit with Apple hosts (next section).

Three caveats matter. First, **not every Android phone exposes the HID Device profile**. Kontroller's README warns that "many device manufacturers disable" it ([Kontroller](https://github.com/mkyybx/Kontroller)). A Fairphone 6 failed while a Galaxy S21 worked **[reported]** ([Fairphone forum](https://forum.fairphone.com/t/bluetoothhiddevice-profile-not-exposed-on-fairphone-6/132462)). Every phone needs a check, and a Play Store compatibility-checker app already exists. Second, **no review we found confirms these apps moving the iPhone AssistiveTouch pointer specifically**. "iOS supported" might only mean the keyboard. Third, the app needs a link from the Mantiza iPhone app to receive commands. Android has a public BLE GATT server ([BluetoothGattServer](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer)), and the iPhone can talk to it with the `bluetooth-central` background mode that the v2 plan already uses for the ESP32. Running Classic HID and a BLE GATT server in the same app at the same time is likely, because they are separate radio modes, but it is **[unconfirmed]**. For background running, the sanctioned approach is a `connectedDevice` foreground service **[confirmed]** ([Android FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types)). A spare phone kept on a charger with battery optimisation turned off should hold the link with its screen off **[unconfirmed]**.

The pointer problems are **the same as with the ESP32**, because the iPhone receives the same HID reports. Relative movement works. An older report says a Bluetooth mouse switched to absolute reports "no longer moved on the iPad" **[reported]** ([Apple Dev Forums 652700](https://developer.apple.com/forums/thread/652700)). The v2 plan's ESP32-S3 evidence for exact positioning is also only a single report. One advantage is that Android makes these HID experiments faster, because you rebuild an app instead of reflashing a board. The spare phone's screen can also show live status and a big Stop button, which replaces the M5StickS3 screen and buttons for free.

## A spare iPhone might work: reconciling the two notes

The two notes disagree. `computers_and_apple_devices.md` says a second iPhone or iPad **cannot** be a HID mouse. `same_iphone_hid.md` says it **plausibly can**. After rereading both, here is how we reconcile them. **The 16-bit block is real and both notes agree on it.** The disagreement is about whether there is a way around it and whether an iPhone host will accept the result. The "no" note relied on the Code=8 errors and on the fact that no App Store app named an iPhone or iPad as a target. It did not look at the 128-bit workaround or at Mobile Mouse. The "yes" note found newer evidence, but every piece of it is single-source, and none of it shows an iPhone as the host.

The evidence on each side, in plain terms:

| Claim | Source | Confidence | What it really shows |
|---|---|---|---|
| Service `1812` (short ID) is blocked on iOS | [Forums 725238](https://developer.apple.com/forums/thread/725238), [Forums 826714](https://developer.apple.com/forums/thread/826714) | **confirmed** (Apple says some services are restricted) | Short ID fails. Apple has not published the list |
| The long ID `00001812-0000-1000-8000-00805F9B34FB` registers, and typing worked on Windows, Android and later macOS | One commenter on [conath gist](https://gist.github.com/conath/c606d95d58bbcb50e9715864eeeecf07) | **reported** (single source) | The blocklist may only check the short form. A later commenter (Sep 2024) could not get a Mac to find the iPhone |
| Bluetouch on an iPad advertised `1812`, seen by Windows and Android but **not** by a Mac | [Forums 725238](https://developer.apple.com/forums/thread/725238) | **reported** | Its working Mac mode had the iPad as *central*, not acting as a mouse. So the "Bluetouch worked with a Mac" claim does not prove iOS-as-HID-peripheral |
| Mobile Mouse Bluetooth: "An iPhone can control a compatible iPad as a Bluetooth mouse and keyboard", no companion software, updated Oct 2026 | [bluetooth.mobilemouse.com](https://bluetooth.mobilemouse.com), [App Store](https://apps.apple.com/us/app/id6749246683) | **reported** (vendor claim) | Best evidence that an Apple *mobile* host accepts an iPhone mouse. Says nothing about iPhone hosts or AssistiveTouch |
| TabletHID: HID-over-GATT "for your PC or Mac", labelled "experimental" | [App Store](https://apps.apple.com/lb/app/tablethid/id6766346670) | **reported** | Shows the trick still passes App Review in 2026. Its targets are computers |
| A Mac publishing a BLE HID service: the iPhone read it, then refused it (`vendorID = 0`, "IOHIDEventDriver start failed"). Apple DTS: "not a formally supported path" | [Forums 848602](https://developer.apple.com/forums/thread/848602) | **reported, with Apple reply** | A warning sign. iPhone hosts may reject app-published HID because the app cannot supply its own Device Information (PnP ID). This case was a gamepad, though, which iOS may treat more strictly |

Our position is that **a spare iPhone as hands is "reported possible for some hosts, unconfirmed for iPhone hosts"**. It is neither ruled out nor proven. The Forums 848602 case gives a concrete technical reason to doubt it. The Mobile Mouse iPad claim gives a concrete reason to hope, because iPadOS and iOS share the same HID stack. The test costs almost nothing: install Mobile Mouse (from $4.99 a month) on iPhone B and try to pair it under AssistiveTouch on iPhone A. Even if it works, it rests on a loophole Apple could close in any iOS release. App Review could also reject our version under 2.5.1's "intended purposes" clause, although three similar apps are currently approved. iOS also limits peripheral advertising in the background, so the helper iPhone would likely need the app open in front, on a charger **[unconfirmed]**. Apple Watch and Apple TV show no sign of working and should be dropped **[unconfirmed]**.

## Macs work at a desk; Windows and Linux add little

A Mac is the strongest "already owned" computer. **KeyPad** (Toolbunch, macOS 11+, free with a $4.99 Pro tier) says it provides "basic mouse functions for iPhones via Assistive Touch" **[confirmed as a vendor claim; quality unconfirmed]** ([App Store: KeyPad](https://apps.apple.com/us/app/keypad-keyboard-and-mouse/id1491684442)). Typeeto does the keyboard half only and was last updated in January 2022 ([Eltima](https://mac.eltima.com/bluetooth-keyboard.html)). These apps most likely use the Mac's Classic Bluetooth HID device role through IOBluetooth, but that is **[unconfirmed]** because neither vendor says how they work. Building our own Mac helper would therefore start with reverse-engineering. Because Mac CoreBluetooth HID was rejected by the iPhone in the Forums 848602 case, the BLE route on the Mac looks worse than Classic. In every case the Mac must be **awake, have Bluetooth on, and be within about 10 m** (Typeeto cites about 32 ft) ([macautomationtips](https://macautomationtips.com/typeeto-easy-remote-typing-on-your-ios-device/)). That makes it a "desk mode", not a pocket product. A user with a Mac could also skip the mouse entirely and drive the phone through iPhone Mirroring or WebDriverAgent from the Mac. That is a different product architecture, and iPhone Mirroring is not available in the EU **[reported]** ([Jean Galea](https://jeangalea.com/control-automate-iphone-webdriveragent/)).

Windows does not block HID (`0x1812`) for GATT apps, but it does reserve the **Device Information Service** **[confirmed]** ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/gatt-server)). A complete HID peripheral needs that service, and we found no Windows project that acts as a mouse for a phone. Linux and Raspberry Pi can advertise as BLE mice with btferret. Its 2025–2026 issues, though, show Apple hosts pairing and then **ignoring the input**, or timing out, while the same code works on Windows and Android **[reported]** ([btferret #79](https://github.com/petzval/btferret/issues/79), [#68](https://github.com/petzval/btferret/issues/68)). Few students keep a spare Pi anyway. One hardware note: iPhone 15 and later accept **wired USB-C mice** for AssistiveTouch **[confirmed]** ([Apple Support 111775](https://support.apple.com/en-us/111775)). A ~$7 Pico 2 W plugged into the port as a USB mouse could be a cheaper, more reliable dongle than a Bluetooth ESP32, but nobody has tested it with an iPhone yet **[unconfirmed]**. It still counts as hardware to buy. Android phones can only act as USB mice with root **[reported]** ([android-usb-gadget](https://github.com/tejado/android-usb-gadget)).

| "Hands" option | Extra purchase | Evidence it drives the iPhone pointer | Main weakness | Our ranking |
|---|---|---|---|---|
| Same iPhone (loopback) | None | None | Blocked twice over | Drop |
| Spare Android phone (Classic HID app) | None if owned | **reported** (apps claim iOS 13+) | Some brands disable the profile; iPhone pointer not yet confirmed | **1st software option** |
| Mac helper (KeyPad-style) | None if owned | **reported** (only explicit AssistiveTouch claim) | Desk only; we must reverse-engineer the method | 2nd |
| Spare iPhone/iPad (128-bit HOGP) | None if owned | **unconfirmed** for iPhone hosts | Loophole; Apple can close it; background limits | 3rd, experimental |
| Windows PC / Linux / Pi | None if owned | None / Apple failures reported | DIS blocked / Apple ignores input | Drop |
| ESP32-S3 (current plan) | ~board cost | **reported** working [v2 plan P8] | Users must buy and pair it | Keep as default |

## Recommended architecture: one command protocol, swappable hands

Treat "hands" as a plug-in, not a fixed device. Inside the Mantiza iPhone app, define one small `Hands` interface: `move(dx, dy)`, `click`, `press`, `drag`, `key(code, modifiers)`, `paste`, `home`, plus `status` and `stop` events coming back. Today's ESP32 already plans to receive these commands over a custom BLE GATT service, with the iPhone as central in the `bluetooth-central` background mode. **Use the exact same GATT service and message format for every helper.** The Android helper app then runs two Bluetooth roles at once. It is a Classic HID mouse and keyboard toward the iPhone, through `BluetoothHidDevice`, and it is a BLE GATT server that receives Mantiza's commands, through `BluetoothGattServer`. A `connectedDevice` foreground service keeps both alive. To the Mantiza app, the Android phone looks exactly like an ESP32 that happens to have a big screen. If tests show that HID and GATT cannot run together on some phones, the fallback channel is a local Wi-Fi WebSocket found by Bonjour/mDNS. That needs iOS's Local Network permission and both devices on one network. The next fallback is a cloud relay through Mantiza's existing backend: about 50–300 ms per command **[unconfirmed]**, which is small next to the screenshot-to-AI loop.

Everything above the hands layer stays the same: screen capture, the AI loop, pointer-finding and correction, and safety. The pointer math does not change either, because the iPhone sees the same relative mouse reports whatever sends them. Onboarding becomes a choice: "Use an old Android phone (free)", "Use a Mac at your desk (free, experimental)", or "Get a Mantiza device". A later spare-iPhone mode would be a "Hands mode" switch inside the same Mantiza iOS app, publishing the 128-bit HID service and the same command service. Build it only if test S3 passes. Ship it as a separate opt-in build if App Review becomes a concern. One licensing note: Bluetooth Remote is GPL-3.0. Use it for testing, but write our own Android helper rather than forking it into closed code **[unconfirmed legal reading; check with an adviser]**.

## Test plan: settle the unknowns in about two weeks

Run the cheap tests that use existing apps first. Only build code for the options that pass. Use an iPhone on iOS 27 as "iPhone A" for every test, with AssistiveTouch on and pairing done under Settings > Accessibility > Touch > AssistiveTouch > Devices > Bluetooth Devices.

| # | Test | How | Pass means | Effort |
|---|---|---|---|---|
| A1 | Android profile check | Install the HID Device Profile Compatibility Checker on 3+ team Android phones (try Samsung, Pixel, and one cheap brand) | Profile exposed on most phones; record which fail | 1 hour |
| A2 | Off-the-shelf Android mouse on iPhone | Bluetooth Remote (F-Droid) and Appground app → pair with iPhone A | Pointer moves, click and long-press work, keyboard types capitals and symbols, ⌘V pastes | 1 day |
| A3 | Reliability | Same pairing; lock iPhone A overnight, reboot the Android phone, toggle Bluetooth | Reconnects without "Forget Device" | 2 days, mostly waiting |
| A4 | Our Android helper prototype | Minimal app: `BluetoothHidDevice` + `BluetoothGattServer` in one foreground service; Mantiza test app sends moves over BLE while another app is in front | Both links stay up for 1 hour with the Android screen off; measure command-to-pointer delay from a screen recording | 3–4 days |
| A5 | Absolute / digitizer descriptor | Swap the report descriptor in the A4 app (absolute mouse, then digitizer) | Pointer jumps to a commanded spot across the whole screen; share the result with the ESP32 track | 1 day |
| S1 | Same-phone loopback | Test app advertises the 128-bit HID service; look in AssistiveTouch Bluetooth Devices on the same phone | Expected to fail; confirms the "drop" | 2 hours |
| S2 | Spare iPhone, off the shelf | Mobile Mouse Bluetooth (monthly plan), TabletHID, Bluetouch on iPhone B → iPhone A. Repeat with an iPad as host as a control | Pointer moves on iPhone A. If it works on the iPad only, iPhone hosts are stricter | 1 day, ~$5 |
| S3 | Spare iPhone, our code | Port the conath gist with the 128-bit UUID and the 0x2908 descriptor fix; confirm on Windows first, then iPhone A; watch iPhone A's logs in Console.app for `vendorID = 0` | No Code=8, and iPhone A accepts input | 2–3 days, only if S2 is unclear or passes |
| M1 | Mac, off the shelf | KeyPad on a team Mac → iPhone A, mouse mode | Pointer moves and clicks | 2 hours |
| M2 | Mac helper feasibility | Only if M1 passes: try the IOBluetooth Classic HID device role in a small Mac app | Our own app drives the pointer | 1 week, stretch goal |

The decision rule: if A2 and A4 pass, ship "use an old Android phone" as the free onboarding path next to the ESP32. If S2 passes on iPhone A, schedule S3 and an App Review probe (an external TestFlight build goes through review). If M1 passes, list Mac desk mode as experimental. If everything except the ESP32 fails, the v2 plan stands unchanged, and we will know exactly why.

## Conclusion

The question shifts from "can software replace the hardware?" to "**which hardware does the user already have?**" A single iPhone can never be its own hands. Apple's blocklist and the Bluetooth link layer both prevent it, and no other on-phone route works without a Mac. But Mantiza's "hands" are just a Bluetooth mouse and keyboard plus a command link, so any device that can play that role works. Android exposes that role through a public API, which makes it the most solid option. The spare-iPhone path is a real, cheap-to-test bet resting on an undocumented loophole, not the dead end one note described or the near-certainty the other suggested. Designing the iPhone app around one shared command protocol now costs little, and it keeps all of these doors open while the ESP32 stays as the fallback that is known to work.

An unexpected bonus: a spare phone used as hands is a *better* status device than the M5StickS3. It has a bigger screen, a bigger battery and a touchscreen Stop button. So the "free" path could also become the nicer one, as long as tests A2 and A4 show that the iPhone's AssistiveTouch pointer really follows it.
